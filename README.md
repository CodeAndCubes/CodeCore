# CodeCore

Общий рантайм для линейки модов Minecraft 1.7.10: реестр сервисов, реестр адаптеров, права, конфиги,
сеть, планировщик, команды. Сам по себе ничего в игре не делает. Это фундамент, на который опираются
CodeChat и остальные.

Подробности устройства и планы в [DESIGN.md](DESIGN.md), перечень нод прав в [perms.md](perms.md).

## Сборка

```bash
./gradlew build                 # компиляция и тесты
./gradlew publishToMavenLocal   # публикация в локальный репозиторий
./gradlew runServer             # запустить сервер разработки
```

Нужен **JDK 25**: GTNH-конвенция компилирует на новейшем toolchain, а байткод понижает до Java 8 через
Jabel. Готовый мод работает на обычной Java 8.

Публикуются три артефакта: сам мод, `codecore-<версия>-api.jar` с одним пакетом `api` и
`codecore-<версия>-platform.jar` с одним пакетом `platform`. Против api компилируются моды-потребители:
типов Minecraft, Forge, netty, LWJGL и Mojang там быть не должно, это стережёт `ImportGateTest`. В
`platform` лежит то, чему тип игры нужен по существу: поиск игрока в сети, ник по идентификатору, переход
от ссылки на игрока к его сущности и от игрового отправителя команды к `CommandSender`. Этот артефакт
берут `compileOnly` и только слои платформы соседних модов:

```groovy
compileOnly 'com.mrleonardos.codecore:CodeCore:0.1.0:api'
compileOnly 'com.mrleonardos.codecore:CodeCore:0.1.0:platform'
```

### Шум в dev-запуске

`runServer` при загрузке пишет вот это, и пугаться не нужно:

```
[FML]: Unable to read a class file correctly
[FML]: There was a problem reading the entry META-INF/versions/17/.../ObjectDeserializer.class
       in the jar ...\night-config\core\3.8.3\...\core-3.8.3.jar - probably a corrupt zip
```

Jar целый. Сканер модов FML читает jar-ы classpath своим ASM 5.0.3, который понимает байткод до Java 8, а
в сыром night-config два класса собраны под Java 17 и лежат в каталоге `META-INF/versions/17`. Загрузка на
этом не останавливается, моды поднимаются.

На сервере такого не будет: в `mods/` лежит собранный jar мода, а из него каталог `versions` выброшен при
шейдинге за ненадобностью. Если строка появится на настоящем сервере, значит это выбрасывание из сборки
пропало.

## Что даёт модам

```java
// права: спрашиваем возможность, не зная, кто её выдаёт
PermissionService permissions = CodeApi.services().require(PermissionService.class);
if (permissions.has(player.getUniqueID(), "mymod.feature")) { … }

// настройки: toml с комментариями, схемой, миграциями и атомарной записью
ConfigFile<MySettings> settings = CodeApi.configs()
    .open(ConfigSpec.of("mymod", "settings", MySettings.class)
        .role(ConfigRoles.CHAT)
        .build());

// сеть: свой канал, обработка уже в главном потоке
NetChannel channel = CodeApi.network().open("mymod");
channel.register(MyPacket.class, PacketSide.SERVER_BOUND);

// команды: дерево подкоманд с правами и автодополнением
CodeApi.commands().register(
    CommandNode.literal("mymod")
        .permission("mymod.admin")
        .child(CommandNode.literal("reload").executes(context -> reload(context))));
```

Свои реализации сервисов нужно регистрировать на инициализации мода, чужие можно запрашивать не раньше
постинициализации: после неё реестр замораживается, и набор реализаций перестаёт зависеть от порядка
загрузки модов.

## Где лежат настройки

Вся линейка живёт в одной папке `config/code`. Область ответственности задаёт подпапку, а имя файла
начинается с владельца, поэтому файлы разных модов в одной папке не сталкиваются.

```
config/code/
├── config.toml                       главный файл линейки
├── core/
│   ├── core-avatars.toml             откуда брать аватары, решает сервер
│   ├── client/core-avatars.toml      предпочтение игрока
│   └── cache/images/                 готовые картинки клиента, не конфиг
└── permissions/
    └── core-groups.toml              группы встроенной реализации прав
```

Правило пути: `config/code/<роль>/<файл>` для настроек сервера, `config/code/<роль>/client/<файл>` для
предпочтений игрока, `<мир>/code/<роль>/<файл>` для состояния, привязанного к миру. Роли пять: `core`,
`permissions`, `economy`, `essentials`, `chat`.

Главный файл собирается из секций, которые приносят моды. Своё ядро держит там `[owners]` (кто держит
роль), `[storage]`, `[audit]`, `[permissions]` и `[images]`. Секция мода, которого сейчас нет на сервере,
остаётся в файле нетронутой вместе со своими комментариями.

Комментарии к своим ключам мод пишет заново при каждой записи, а строки, дописанные человеком, и
незнакомые ключи остаются на месте.

## Кто держит роль

Права, экономику и перемещения держит один владелец на роль, и выбирается он именем в секции `[owners]`
главного файла:

```toml
[owners]
permissions = "auto"
economy = "auto"
essentials = "auto"
```

Значений три: `auto` (наш мод, если он стоит, иначе встроенная реализация ядра), `off` (роль не занята
никем) и имя владельца, например `luckperms`. Незнакомое имя и имя мода, которого на сервере нет, уводят
роль по правилу `auto` с записью в лог: молча оставить сервер без прав из-за опечатки хуже.

У прав `off` не оставляет сервер без администрирования: ядро считает права по списку операторов, как
ванильный Minecraft без модов прав. Оператор получает любое право, остальные не получают ни одного,
групп и меты нет. Роль при этом ничья, и стартовая строка говорит об этом прямо.

У роли есть перечень умений, а каждый претендент называет своё подмножество. Разница и есть то, что на
сервере не работает: подсистемы и команды, которые держатся на недостающем умении, не регистрируются, а
перечень уходит в лог при старте и показывается по `/codecore adapters`. Отдав роль, наш мод отходит
целиком: не регистрирует команд, не открывает своих файлов и не трогает те, что уже лежат на диске.

## Права

Файл `config/code/permissions/core-groups.toml`: группы с наследованием, правила с точками и звёздочками,
запрет через `-`, метаданные вроде префикса и цвета ника.

```toml
[groups.player]
inherits = []
nodes = ["codechat.channel.global.*"]

[groups.player.meta]
prefix = ""

[groups.admin]
inherits = ["player"]
nodes = ["*"]

[groups.admin.meta]
prefix = "&c[A] "

[players]
```

Группы по умолчанию лежат не здесь, а в секции `[permissions]` главного файла: `defaultGroup` для игрока,
которому ничего не выдали, и `opGroup` для оператора сервера из `ops.json`.

Из подходящих правил выигрывает самое точное, при равной точности побеждает запрет. Личные правила
игрока сильнее групповых.

Это встроенная реализация. CodePerms при заводском `auto` забирает роль себе, и код, который спрашивает
права, не меняется.

### Готовые адаптеры

Права можно взять из чужого мода: в секции `[owners]` у ключа `permissions` пишется имя владельца. Сам по
себе, без имени в конфиге, ни один адаптер не подключается. К чужим модам ядро не привязано: классы
ищутся по имени, и отсутствие мода означает лишь, что заявка недоступна, а роль ушла по правилу `auto`.

| Имя в `[owners]` | Как берутся права | Оговорка |
|---|---|---|
| `luckperms` | кэш прав пользователя (`getCachedData`), группа из `getPrimaryGroup`, мета из `getMetaValue` | незагруженный пользователь считается бесправным |
| `ultramine` | `PermissionHandler.hasGlobally` и `getMeta` по нику | ник берётся у игроков в сети и из кэша профилей сервера |
| `forgeessentials` | `APIRegistry.perms`: `checkUserPermission`, `getPrimaryGroup` и `getUserPermissionProperty` по паре из uuid и ника | поле пустует, пока модуль прав FE не поднялся, поэтому читается перед каждым вопросом; сроков, треков и контекстов в его api нет вовсе |

Ни один из трёх не умеет контексты, временные выдачи и треки: этих умений у роли они не закрывают.

## Клиентская часть

Всё, что связано с экраном, живёт в `api.client` и поднимается только на клиенте, а в серверный jar эти
классы не попадают вовсе.

```java
// картинка любого формата и размера, приведённая к квадрату
ImageHandle avatar = ClientApi.images()
    .request(ImageRequest.of(ImageSource.url("https://site/av/Steve.webp"), 64));
if (avatar.ready()) {
    Images.draw(avatar.texture(), x, y, 64);
}

// аватар игрока по настроенному источнику
ImageHandle handle = ClientApi.avatars().avatar(playerId, playerName, 16);
```

Читаются png, jpeg, gif и webp. Картинка скачивается в фоновом потоке, обрезается по центру до квадрата,
уменьшается ступенями (иначе 4K превращается в кашу), кладётся в `config/code/core/cache/images` и уже
оттуда попадает в видеопамять. Повторная просьба о том же источнике не порождает вторую загрузку, а
неудачный адрес не трогается пять минут.

Пределы жёсткие: 2 МБ на файл, 16 мегапикселей на исходник, сторона готовой картинки до 512 пикселей,
256 картинок в памяти, таймауты на соединение и чтение. Секция `[images]` главного файла эти значения
только опускает: поднять их выше заводских нельзя, иначе настройка с сервера становится способом занять
чужую память.

### Откуда берутся аватары

Решает **сервер**. Файл `config/code/core/core-avatars.toml` лежит на сервере и рассылается клиентам при
входе:

```toml
provider = "urlTemplate"
url = "https://site/avatars/{name}.png"
size = 64
```

`provider` бывает `urlTemplate` (подстановки `{name}`, `{uuid}`, `{uuid_nodash}`), `jsonEndpoint` (сначала
запрос json, адрес картинки берётся по `jsonPath`), `localFolder` (папка у игрока, по умолчанию
`config/code/core/avatars`) или `none`. После правки файла нужно выполнить `/codecore reload`, и следующий
вошедший получит новую настройку.

Пока сервер не пришлёт настройку, клиент аватаров не показывает вовсе, а незнакомый провайдер, размер за
границами или адрес не по http и https превращаются в «выключено» ещё до применения: настройка приходит
по сети, и доверять ей на слово нельзя. У себя игрок может только отказаться от аватаров совсем (файл
`config/code/core/client/core-avatars.toml`, единственное поле `enabled`); сервер это решение не
перебивает.

Свой источник добавляется из кода через `ClientApi.avatars().addProvider(...)`: он спрашивается раньше
серверного и переключением сервера не сбрасывается.

Для интерфейса есть `Draw` (прямоугольники со скруглением, линии, тень, обрезка по области), `Theme`
(палитра и размеры), `Images`, `PlayerHead` (лицо из скина и заглушка с буквой ника), `ContextMenu`,
`Animated` с `Easing` (значение, которое доезжает до цели по часам, а не по тикам) и `Blur`, который
размывает то, что уже нарисовано под панелью.

`Blur` спрашивают через `available()`: шейдеры есть не везде, и на отказ нужно рисовать обычную подложку,
иначе прозрачная дыра сделает текст нечитаемым на светлом фоне.

## Раздельные jar

Сборка выдаёт `CodeCore-<версия>-client.jar` и `-server.jar`: клиентские пакеты помечены `@ClientSide` и
физически вырезаются из серверного. Универсальный jar остаётся для разработки и одиночной игры.

## Команды ядра

| Команда | Право | Что делает |
|---|---|---|
| `/codecore reload` | `codecore.admin.reload` | перечитывает файлы настроек всех модов |
| `/codecore adapters` | `codecore.admin.adapters` | по строке на роль: владелец, как выбран, кандидаты, недоступные умения |
